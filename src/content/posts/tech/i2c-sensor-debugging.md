前阵子给一块开发板接了个 I2C 环境传感器，代码是从厂商示例改的，
编译下载一切正常，但读出来的数据全是 `0xFF` 或者干脆超时。

这个过程折腾了大半天，最后发现是个很蠢的问题。
但正因为蠢，才值得写下来——**嵌入式调试的坑，八成都在你没想到的地方**。

## 一、先怀疑硬件，再怀疑代码

这是最重要的一条经验，顺序不能反。

新手遇到读不出数据，第一反应是去翻代码、翻数据手册看时序。
但根据我的经验，**接线问题占了至少一半**。

### 检查清单（按顺序，别跳步）

1. **供电电压对不对**。3.3V 的传感器接 5V，运气好是没反应，
   运气不好直接冒烟。先用万用表量 VCC 和 GND 之间的实际电压。
2. **GND 有没有共地**。两块板子各自供电但不共地，
   I2C 电平没有参考点，波形全是乱的。这个坑我踩过两次。
3. **SDA/SCL 有没有接反**。看起来像废话，但排针丝印标错、
   或者杜邦线颜色不统一的时候，真的很容易反。
4. **上拉电阻有没有**。I2C 是开漏输出，**必须有上拉电阻**才能拉高。
   很多模块自带 4.7k 上拉，但如果你从裸芯片自己搭，就必须外接。
   没有上拉的直接表现就是：波形永远拉不高，读出来全 0。

> 我这次的问题就是第 4 条。模块上有上拉，但我从另一块板上引了
> 一组 I2C，那组线上没有上拉电阻，而且是长杜邦线，容性负载大，
> 边沿变得很缓。**同样的代码，换一组引脚就好了**——
> 这也是为什么"换个接口试试"是个值得养成的习惯。

## 二、用工具确认，而不是猜

### 万用表：先解决"有没有电"

最低成本的工具，但很多人跳过这步。
量三个值：VCC-GND 电压、SDA-GND 静态电压、SCL-GND 静态电压。

**空闲状态下 SDA 和 SCL 都应该是高电平**（被上拉电阻拉高）。
如果量出来是 0V 或者中间值，说明上拉有问题或者线短路了，
这时候再去调代码是浪费时间。

### 逻辑分析仪：看时序

几十块钱的 8 通道逻辑分析仪就够用，配合 **PulseView**（sigrok 项目）软件。

抓 I2C 的关键是**看三个东西**：

1. **起始条件**：SCL 高电平时 SDA 从高变低
2. **地址字节**：7 位地址 + 1 位读写标志，然后看**从机有没有拉低 ACK**
3. **时钟频率**：标准模式 100kHz，快速模式 400kHz

```
逻辑分析仪的 I2C 解码器会直接告诉你：
  Start
  Address: 0x76 (Write)     ← 地址对不对？
  ACK                        ← 从机应答了吗？没应答就是 NAK
  Data: 0xF4
  ACK
  ...
```

**这次排查中最有用的一步**：逻辑分析仪显示地址发出后是 **NAK**（无应答）。
NAK 的含义很明确——**总线上没有设备响应这个地址**。

有了这个信息，问题范围立刻缩小到三种可能：

- 地址错了（比如手册写 0x76，实际 7 位地址是 0x76 >> 1 = 0x3B）
- 设备根本没上电
- 接线错了

**7 位地址和 8 位地址的混淆是经典坑**。数据手册经常写 8 位地址
（含读写位），而代码里要传 7 位。0x76 和 0xEC 就是同一个设备的两种写法。
我这次就是栽在这——手册给的 0x76 已经是 7 位地址，
但我照抄了一个把地址左移一位的示例代码。

### 示波器：看信号质量

逻辑分析仪只能看逻辑电平（高/低），看不到**边沿质量**。
如果上拉电阻太大或者线太长，边沿会变成圆弧状，
在某个阈值附近抖动，逻辑分析仪就会解码出错误的位。

示波器能看出：

- 上升时间是不是太长（超过 1μs 就要警惕）
- 有没有过冲、振铃
- 高电平到底是多少伏（3.3V 系统的 VIH 通常要求 > 2.0V）

## 三、代码侧的自查顺序

硬件确认没问题后，再来看代码。按这个顺序查：

```c
// 1. 时钟频率配置对不对
//    很多 MCU 的 I2C 外设需要手动开时钟，忘了就是完全没波形
RCC_APB1PeriphClockCmd(RCC_APB1Periph_I2C1, ENABLE);

// 2. 引脚复用有没有配对
//    配了 I2C1 的时钟，但引脚还在当普通 GPIO 用，这是常见错误
GPIO_PinAFConfig(GPIOB, GPIO_PinSource6, GPIO_AF_I2C1);

// 3. 引脚模式必须是复用开漏，不是推挽
//    推挽模式下两个设备同时输出会短路
GPIO_InitStruct.GPIO_Mode = GPIO_Mode_AF_OD;

// 4. 地址补零与否，取决于库函数约定
//    HAL 库要求左移一位后的 8 位地址
#define SENSOR_ADDR (0x76 << 1)
```

**每一步都要用逻辑分析仪验证**：配完时钟应该有波形，
配完引脚应该有正确波形。不要一次改五处然后一起试——
那样成功了也不知道是哪一处的功劳，失败了也不知道是哪里的问题。

## 四、串口日志：便宜好用的调试手段

逻辑分析仪不是随时都有，但串口几乎每块板子都引出来了。
**在 I2C 读写的每一步前后打日志**，能快速定位卡在哪：

```c
printf("[I2C] init done\n");
uint8_t id = 0;
if (i2c_read_reg(SENSOR_ADDR, REG_CHIP_ID, &id) != 0) {
    printf("[I2C] read CHIP_ID failed\n");
} else {
    printf("[I2C] CHIP_ID = 0x%02X\n", id);
}
```

读 `CHIP_ID`（芯片 ID 寄存器）是最好的第一步——
**它的值是固定的、数据手册上写死的**。
如果读出来和手册一致，说明通信完全正常，问题在后面的数据处理；
如果不一致或者读不到，问题就在通信层。

这个技巧能帮你**一刀切开"通信问题"和"逻辑问题"**，
省下大量瞎猜的时间。

## 五、这次排查的完整时间线

复盘一下，我浪费的时间主要在哪：

| 阶段 | 耗时 | 是否必要 |
|---|---|---|
| 改代码、翻数据手册 | 2 小时 | ❌ 应该先查硬件 |
| 万用表量电压 | 5 分钟 | ✅ 必要，但做得太晚 |
| 逻辑分析仪抓波形 | 15 分钟 | ✅ 直接定位到 NAK |
| 查出地址左移错误 | 10 分钟 | ✅ |
| 换一组带正确上拉的 I2C 引脚 | 5 分钟 | ✅ |

**如果一开始就按"供电 → 接线 → 波形 → 代码"的顺序走，
半小时就能解决。**

## 六、留一份自己的检查清单

我现在遇到"外设没反应"时的固定流程：

1. 万用表：VCC 电压、GND 共地、空闲电平
2. 逻辑分析仪：有没有波形？有没有 ACK？时钟频率对不对？
3. 读 ID 寄存器：通信层和逻辑层的分界线
4. 换一组引脚/换一块模块：快速排除硬件个体问题
5. 最后才动代码，而且**一次只改一处**

第 4 条特别值得强调：**手里有多余的模块时，"换一个试试"比debug 半小时更快**。
嵌入式调试最忌讳的就是在"我确定硬件没问题"这个假设上死磕。
