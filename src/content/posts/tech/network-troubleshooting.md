"网络不通"这四个字，是运维现场信息量最低的一句话。

网线没插、防火墙策略、DNS 解析、TLS 证书、应用配置写错，都会说成"不通"。唯一能提高效率的办法是把它按层次切开，一段一段地排除。

下面这六段是固定的，顺序也基本固定。麻烦的是每一段里都有几个"看起来正常但其实没证明任何事"的陷阱。

## 先问清楚"不通"到底是什么

这一步最省时间，也最常被跳过。

我一般会问三个问题：

1. 谁不通谁。一台设备、一个网段，还是只有某个方向？
2. 什么不通。ping 不通，还是网页打不开，还是 SSH 连不上？
3. 什么时候开始的。一直这样，还是突然断的？

有个案例我到现在还记得。客户报了"打不开网页"，我们查了两小时，最后发现是只有某一个站点打不开，其他网站都正常。故障范围从一开始就理解错了，排查方向自然也全错。

如果你只能问一个问题，问这个：

> 换一台设备、换一个网络，现象一样吗？

这一个问题就能把"全网故障"缩小到"单机故障"，省掉的往往是几十分钟。

## 一、链路层：线到底通不通

先看网卡的物理状态。

```bash
ip -s link show eth0
ethtool eth0 | grep -E "Speed|Duplex|Link detected"
```

```
Speed: 100Mb/s
Duplex: Half
Link detected: yes
```

千兆环境里协商成百兆、或者双工显示 Half，基本都是线缆或接口的问题。可能是网线本身规格不够，可能水晶头没压好，也可能接口氧化。

其中**双工不匹配**最容易被忽略。它的表现很有欺骗性：小包（比如 ping）一切正常，一旦有大流量就开始丢包重传，用户的感觉是"能上网，但打开网页特别慢"。这种症状很容易被误判成"网站慢"，从而查错方向。

顺手说一句，`ifconfig` 可以不用了。`ip` 和 `ethtool` 给的信息多得多。

## 二、IP 层：ping 能证明什么

这是整篇里我最想说清楚的一段。

`ping` 通只证明一件事：ICMP Echo Request 到了对面，Echo Reply 回来了。

它不证明：

- 端口开着。22、80、443 通不通跟 ICMP 一点关系没有
- 应用正常。服务进程挂了照样能 ping 通
- 带宽够用
- 链路稳定。一次成功不代表持续不丢包

所以"能 ping 通"这个结论的价值比大多数人以为的低很多。反过来也一样：ping 不通不代表有问题，很多服务器是故意禁 ICMP 的，它上面的 Web 服务可能好好的。

真正有用的几个用法：

```bash
# 别 ping 四下就下结论，跑够次数看丢包率
ping -c 100 10.10.122.1

# 多网卡机器上必须指定源地址，否则可能从错误的网卡发出去
ping -I 192.168.10.50 10.10.122.1

# 大包探测 MTU 和分片问题
ping -M do -s 1472 10.10.122.1
```

最后这条值得展开。`-s 1472` 是 ICMP 载荷长度，`-M do` 禁止分片。1472 加上 8 字节 ICMP 头、20 字节 IP 头，正好 1500，也就是一个标准以太网帧。

如果这个尺寸能通、更大的包不通，说明链路上有 MTU 限制。PPPoE、各种隧道、VPN 都会造成这种情况。

```
$ ping -M do -s 1472 10.10.122.1
ping: local error: message too long, mtu=1492
```

`mtu=1492` 这个数字一看就知道是 PPPoE。这时候如果应用层还以为自己能发 1500 的包，大包会被静默丢掉，现象就是"小请求正常、大请求卡死"。这是 PMTUD 黑洞，查起来很费时间，但知道了就很快。

## 三、路由：包走的路对不对

`traceroute` 用得很多，但它的误导性也很强。

中间出现 `* * *` 不代表故障。那只是某一跳没有回 ICMP Time Exceeded，很多路由器和防火墙默认就不回，或者对这类回复做了限速。中间全是星号、最后一跳能到，是完全正常的情况。

```
$ traceroute 8.8.8.8
 1  10.10.122.1        2.1 ms
 2  * * *
 3  202.96.x.x        12.4 ms
 4  8.8.8.8           28.7 ms
```

只看最后一跳，别被中间的星号带偏。

比 `traceroute` 好用得多的是 `mtr`。traceroute 是一次性快照，mtr 是持续统计，能看出丢包是从哪一跳开始出现的。

```bash
mtr -r -c 100 8.8.8.8
```

```
HOST                Loss%   Snt   Last   Avg  Best  Wrst
1. 10.10.122.1       0.0%   100    2.1   2.3   1.8   5.2
2. 202.96.x.x        0.0%   100   12.4  12.9  11.2  35.1
3. 61.x.x.x          2.0%   100   13.1  14.0  11.8  89.3
4. 8.8.8.8           2.0%   100   28.7  29.5  27.1 120.4
```

读法是看丢包率有没有逐跳累加。第 3 跳开始丢 2%，第 4 跳还是 2% 没有变多，说明这个丢包是第 3 跳引入的。如果第 3 跳显示 2% 但第 4 跳回到 0%，那只是第 3 跳不优先处理 ICMP 探测包，不是真丢包。

## 四、端口：服务在不在

ping 通只能说明 IP 可达。业务是从端口进的。

```bash
nc -zv 10.10.122.50 443
nc -zv 10.10.122.50 3306
nc -zv 10.10.122.50 22 80 443 3306
```

`nc` 的结果有三种，含义完全不同：

| 结果 | 含义 | 该往哪查 |
|---|---|---|
| `succeeded` | TCP 握手完成 | 问题在应用层 |
| `Connection refused` | 对方回了 RST | 主机活着，没有程序监听这个端口 |
| `Connection timed out` | 没有任何回应 | 被防火墙丢弃，或者路由不通 |

这个区分帮我省过很多时间。

有一次客户说数据库连不上，我在他机器上 `nc` 了一下，返回 `refused`。包到了主机、主机主动拒绝，说明网络这一段是好的，只是没有进程在监听。直接让他去启动 MySQL，几十秒结束。如果我当时按"网络不通"的思路去查防火墙，大概要折腾很久。

`refused` 是网络通的证据，不是网络故障的症状。

## 五、DNS：名字解析对不对

前面四段都正常，网页仍然可能打不开。

```bash
nslookup feiyuqifei.github.io 8.8.8.8
dig feiyuqifei.github.io @1.1.1.1 +short
dig feiyuqifei.github.io +trace

# 关键：本地解析结果和公共 DNS 是否一致
dig feiyuqifei.github.io +short
dig feiyuqifei.github.io @8.8.8.8 +short
```

两条命令的结果不一样，说明本地 DNS 有问题。可能是缓存、可能配置指向了错误的服务器、也可能是被劫持。这个对比法一眼就能定性。

顺便澄清一个常见误解。"能 ping 通 IP 但 ping 不通域名"不代表网络有问题，它只说明 DNS 这一环断了。反过来也成立：`nslookup` 能解析出地址，不代表那个地址可达。这两件事互不相干。

## 六、应用层：抓包看握手

前五段都正常，问题就在应用层。这时候该抓包了。

```bash
tcpdump -i eth0 -nn -s0 -w /tmp/cap.pcap 'tcp port 443'
tcpdump -i eth0 -nn 'tcp port 443' -c 50
```

TLS 握手失败的抓包有一个很典型的形状：

```
10.10.122.50.54321 > 93.184.216.34.443: Flags [S], seq 1234567
93.184.216.34.443 > 10.10.122.50.54321: Flags [S.], seq 7654321, ack 1234568
10.10.122.50.54321 > 93.184.216.34.443: Flags [.], ack 1
10.10.122.50.54321 > 93.184.216.34.443: Flags [P.], length 517
```

TCP 三次握手完成了（`[S]`、`[S.]`、`[.]` 三行），客户端也把 Client Hello 发出去了（`length 517`），然后没有任何回应。

看到这个形状，基本可以排除网络层。包到了对面，对面不回，通常是 SNI 被中间设备按域名拦了、或者服务端证书配置有问题直接拒绝。问题范围从"网络不通"缩小到了"TLS 或策略"，差一步就能定位。

## 一份可以直接照着走的清单

按顺序，别跳步：

1. 问清楚不通的具体含义。谁、什么协议、什么时候开始、范围多大
2. 换设备或换网络复现，先分清单机还是全网
3. `ethtool` 看速率和双工
4. `ping` 跑够次数看丢包，大包测 MTU
5. `mtr` 看丢包从哪一跳开始
6. `nc -zv` 区分 `refused` 和 `timed out`
7. 本地 DNS 和公共 DNS 结果对比
8. `tcpdump` 看握手和 TLS 有没有完成

每一步"看起来正常"的时候，都要问一句它究竟证明了什么。这是这份清单唯一的使用要点。

## 两个习惯

**先定性，再定量。** 别一上来就对着十六进制看。先确定断在哪一层，再往下钻。分层的意义就在这里。

**一次只改一处。** 我早年犯过的错：同时改了防火墙、DNS 和路由，问题消失了，但完全不知道是哪一处起的作用。两个月后同样的问题再来一次，还是不会查。

修好是今晚能下班，搞清楚是明年不用再加班。这两件事都值得做，但顺序不能反。
