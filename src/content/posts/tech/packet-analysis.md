我见过两种极端。

一种是**从不动抓包**的人。他们排障靠猜：
重启一下、换根网线、把防火墙关了试试。
有时候能碰对，但下次遇到同样的问题还是不会查。

另一种是**抓包上瘾**的人。一有问题就开 Wireshark，
抓下来几万个包，在十六进制里翻两个小时，
最后发现是网线没插好。

**抓包是手段，不是目的。** 这篇讲的是怎么用最少的时间
从包里得到确定的答案 —— 以及什么时候根本不该抓。

## 一、先想清楚"要证明什么"

这是最重要的一步，也是最多人跳过的一步。

抓包之前必须能回答：

> **如果这个问题是 X 导致的，抓包里应该看到什么？**

回答不出来，说明你还没想清楚，抓了也白抓。

举几个例子：

| 怀疑的问题 | 抓包里应该看到 | 抓包位置 |
|---|---|---|
| 客户端根本没发包 | 抓不到任何 SYN | 客户端本机 |
| 服务端收到了但不回 | 有 SYN，无 SYN-ACK | 服务端本机 |
| 中间被防火墙丢了 | 客户端发出 SYN，服务端抓不到 | **两端同时抓** |
| TLS 握手失败 | TCP 通了，Client Hello 后无响应 | 客户端或服务端 |
| 丢包重传 | 大量 `[TCP Retransmission]` | 两端对比 |

**注意第三行**：判断"中间设备丢包"，**必须在两端同时抓**，
然后在时间线上对齐。只抓一端，你无法区分
"客户端没发"和"发了但没到"。

这是抓包分析里最有价值的技巧之一，
也是最容易被忽略的 —— 很多人只在一台机器上抓，
然后对着"没有响应"得出错误结论。

## 二、在哪里抓：三个位置的选择

| 位置 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **端点本机** | 能看到进程与包的对应关系，无额外设备 | 看不到被本机防火墙丢弃的包 | 应用层问题 |
| **交换机镜像口** | 能看到真实链路上的全部流量 | 需要交换机支持、需要配置 | 中间链路问题 |
| **网关/防火墙上抓** | 能看到跨网段流量 | 流量大、噪音多 | 路由与策略问题 |

**我的默认选择是"两端同时抓"**：

```bash
# 客户端
tcpdump -i eth0 -nn -s0 -w client.pcap host 93.184.216.34 and port 443

# 服务端
tcpdump -i eth0 -nn -s0 -w server.pcap host 10.10.122.50 and port 443
```

然后同时开始、同时停止、比对时间戳。

> **一个前提**：两端时钟要大致同步。
> 差几秒就会让时间线对齐变成猜谜。
> 生产环境应该配 NTP —— 这本身就值得单独做一件事。

## 三、tcpdump:服务器上的主力

服务器通常没有图形界面，`tcpdump` 是唯一选择。
**先记住 `-nn` 和 `-s0`**：

- `-nn`：不解析主机名和端口名。不做 DNS 反查，输出快且不会被 DNS 问题拖住
- `-s0`：抓完整包，不截断。默认可能只抓 96 字节，抓不到后续数据

### 我常用的几个组合

```bash
# 1. 抓某个主机的 443 流量，写文件
tcpdump -i eth0 -nn -s0 -w cap.pcap host 93.184.216.34 and port 443

# 2. 只抓 SYN 包（看有没有人尝试连接，噪音极小）
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'

# 3. 排除 SSH，避免把自己踢下线时抓不到证据
tcpdump -i eth0 -nn -s0 -w cap.pcap not port 22

# 4. 抓 ICMP（看是否有 unreachable 报文回来 —— 极有价值）
tcpdump -i eth0 -nn icmp

# 5. 按大小过滤，只看大包（找 MTU 相关问题）
tcpdump -i eth0 -nn 'greater 1400'
```

**第 4 条特别值得单独说。**

当路由不可达或端口关闭时，中间设备会回一个
**ICMP Unreachable**。这个报文里包含了"哪一跳、
为什么不可达"，是定位问题的金矿：

```
ICMP 10.10.122.1 unreachable - need to frag (mtu 1492)
ICMP 10.10.122.1 unreachable - admin prohibited filter     ← 被策略拒绝
ICMP 10.10.122.1 unreachable - host unreachable
```

`admin prohibited filter` 明确告诉你"有防火墙策略挡了"，
`need to frag (mtu 1492)` 明确告诉你 MTU 问题。
**省掉大量猜测。**

### 一个容易踩的坑：抓包时的缓冲

`tcpdump` 写文件时有缓冲。如果抓完直接 `Ctrl+C`，
缓冲区里的包可能丢。

```bash
# 加 -U 让每个包立即写盘（不缓冲）
tcpdump -i eth0 -nn -s0 -U -w cap.pcap host 10.10.122.50
```

抓重要证据时我总加 `-U`。丢几个包可能就丢掉了关键的那个。

## 四、Wireshark：分析而不是抓

**Wireshark 最大的价值是分析，不是抓包。**
在服务器上抓、下载到本机用 Wireshark 看，是最实用的组合。

### 三个必装的列

默认列不够用。我固定加这三列：

| 列 | 字段 | 为什么 |
|---|---|---|
| 时间（相对） | `frame.time_relative` | 绝对时间看不出间隔，相对时间一眼看到"卡了 3 秒" |
| TCP 流索引 | `tcp.stream` | 一键把同一条连接的所有包挑出来 |
| Delta 时间 | `tcp.time_delta` | 相邻包的时间差，卡顿立刻现形 |

`tcp.stream` 这个特别有用 —— 右键任意包 →
**Follow → TCP Stream**，就把这条连接的完整对话
按两个方向分别列出来了。**看应用层协议最快的方式。**

### 真正好用的过滤器（按使用频率）

```
# 按连接
tcp.stream eq 5                          # 第 5 条连接的全部包
ip.addr eq 10.10.122.50 and tcp.port eq 443

# 只看异常（这几个是我最常用的）
tcp.analysis.flags                      # 所有 TCP 异常标记
tcp.analysis.retransmission             # 重传
tcp.analysis.duplicate_ack              # 重复 ACK（对端没收到）
tcp.analysis.zero_window                # 接收窗口为 0（对端处理不过来）
tcp.flags.reset eq 1                    # RST 包

# 应用层
tls.handshake.type == 1                 # Client Hello
tls.alert_message                       # TLS 告警（握手失败的证据）
http.response.code >= 400               # HTTP 错误响应
dns.flags.rcode != 0                    # DNS 解析失败

# 组合：只看某条连接里的重传
tcp.stream eq 5 and tcp.analysis.retransmission
```

**我最常用的一个过滤器是 `tcp.analysis.flags`** ——
它把 Wireshark 判定为"异常"的包全挑出来。
一个健康的连接应该几乎没有这类包。

### 四个"异常标记"的含义

| 标记 | 中文 | 说明什么 |
|---|---|---|
| `[TCP Retransmission]` | 重传 | 发送方没收到 ACK，重发了。**网络丢包或对端慢** |
| `[TCP Dup ACK]` | 重复确认 | 接收方在催"我还没收到第 N 个包"。**中间丢包** |
| `[TCP ZeroWindow]` | 零窗口 | 接收方缓冲区满了，"先别发"。**对端应用处理不过来** |
| `[TCP Out-Of-Order]` | 乱序 | 包到达顺序乱了。**多路径或负载均衡常见** |

**这四个的区分非常重要**，因为它们指向完全不同的根因：

- 大量 `Retransmission` + `Dup ACK` → **网络丢包**，查链路
- 大量 `ZeroWindow` → **应用太慢**，查服务端性能，不是网络问题
- 只有 `Out-Of-Order` → 通常是**正常现象**，别追

我见过有人看到重传就去找网络部门，
结果根因是数据库查询慢导致应用不读 socket，
接收窗口打满。**方向错了，怎么查都是白费。**

## 五、时间线分析：找"那三秒"

抓包分析的核心技能是**看时间间隔**，而不是看内容。

一个典型的例子：

```
No.   Time      Delta    Source        Destination   Info
1     0.000000           10.10.122.50  93.184.216.34 TCP 54321→443 [SYN]
2     0.028000  0.028    93.184.216.34 10.10.122.50 TCP 443→54321 [SYN, ACK]
3     0.028100  0.0001   10.10.122.50  93.184.216.34 TCP 54321→443 [ACK]
4     3.041200  3.0131   10.10.122.50  93.184.216.34 TLSv1.3 Client Hello
```

**第 4 行的 Delta 是 3.01 秒** —— 三次握手完成后，
客户端等了 3 秒才发 Client Hello。

这个 3 秒**不是网络问题**（前三个包只用了 28 毫秒），
而是**客户端自己卡了 3 秒**才发出请求。
可能是 DNS 查询、可能是某个同步调用、可能是 GC。

**没有 Delta 列，这个 3 秒就藏在"看起来都正常"的包里。**

> `3.0 秒` 这个数字有特殊的味道 —— 它太规整了，
> 通常意味着**某个超时或重试机制**，而不是随机卡顿。
> 看到整齐的秒数，就往"重试/超时"方向想。

## 六、什么时候不该抓包

这部分很少有人写，但同样重要。

**不该抓的情况**：

1. **问题能通过日志定位** —— 应用日志里有明确报错，
   先读日志。抓包比读日志慢十倍。
2. **流量太大** —— 万兆链路上的抓包会瞬间写满磁盘，
   而且过滤出有用信息极难。先用统计工具（`nstat`、`ss -s`）看趋势。
3. **加密流量且没有密钥** —— 你只能看到包的大小和时间，
   看不到内容。这时候该去查应用日志和服务端指标。
4. **已经知道根因** —— 定位到了就别再抓了，去修。

**抓包适合的场景**：

- 两端对"谁先没响应"各执一词
- 怀疑中间设备（防火墙、负载均衡）行为异常
- 应用层协议交互异常，但两端日志都"正常"
- 需要一份**可留存的证据**（抓包文件能发给别人看）

最后一条常被低估：**抓包文件是能当证据的**。
"我说你丢了包"和"这是抓包，第 142 个包你发了，
我这边没收到"，说服力完全不同。

## 七、我的抓包流程

1. **写出假设**：如果问题是 X，抓包里应该看到什么
2. **选位置**：端点 / 镜像口 / 网关，必要时两端同时抓
3. **写过滤器**：在抓的时候就过滤，比事后过滤高效得多
4. **加 `-U`**：确保不丢包
5. **加 `-nn -s0`**：不解析、不截断
6. **先看时间线**：加 Delta 列，找异常的间隔
7. **再看异常标记**：`tcp.analysis.flags` 一眼扫过
8. **追单条流**：Follow TCP Stream 看应用层对话
9. **留证据**：保存 pcap 文件，记下抓包时间点和过滤条件

第 1 步和第 9 步是最容易被跳过的，也是最能省时间的。

## 最后：一句反直觉的话

**抓包高手和新手的区别，不在于能看懂多少协议细节，
而在于知道什么时候不需要抓包。**

大部分"网络问题"最后都不是网络问题 ——
是应用慢、是配置错、是磁盘满、是证书过期。
抓包是排除法里的一个环节，不是万能钥匙。

**先想，再抓。** 想清楚要证明什么，
一次抓包就能给出答案；想不清楚，
抓十次也只是在数据里游泳。
