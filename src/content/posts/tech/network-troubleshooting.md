"网络不通"这四个字，是运维现场最没有信息量的一句话。

它可能是网线没插，也可能是防火墙策略、DNS 解析、
TLS 证书、甚至应用层的一个配置项。**把它逐个层次切开，
是排障效率的唯一来源。**

这篇按 OSI 的层次往下走，每一层给一个"能判定"的方法。
不列命令大全 —— 而是说清**每个命令能证明什么、不能证明什么**。

## 第零步：先问清楚"不通"是什么

这一步最省时间，但最常被跳过。必须逼出三个具体信息：

1. **谁不通谁？**（单台设备 / 整个网段 / 只有某个方向）
2. **什么协议不通？**（ping 不通？网页打不开？SSH 连不上？）
3. **什么时候开始的？**（一直这样 / 突然断的 / 某个时间点后）

我遇到过一个案例，折腾了两小时，最后发现是
"用户说打不开网页，其实是只有某个站点打不开" ——
**范围完全不同，排查方向也就完全不同。**

> **一个立竿见影的提问**：
> "换一台设备、换一个网络，现象一样吗？"
> 这一个问题就能把问题从"全网故障"缩小到"单机故障"。

## 岔路口一：链路层 —— 线通不通

**判定方法**：看网卡的状态和速率。

```bash
# Linux：看 link 是否 UP，协商速率和双工
ip -s link show eth0
ethtool eth0 | grep -E "Speed|Duplex|Link detected"
```

```
Speed: 100Mb/s
Duplex: Half          ← 危险信号
Link detected: yes
```

**看到 `Half` 或速率明显低于预期，八成是线缆或接口问题。**

千兆环境协商成百兆，通常是：
- 网线是超五类以下，或者某一对线序错了
- 接口氧化、水晶头没压好
- 一端强制、一端自适应（**双工不匹配**）

**双工不匹配是经典杀手**：小包（ping）正常，
大流量时大量丢包和重传。表现是"能 ping 通，但打开网页极慢"。

> 别用 `ifconfig` 了。`ip` 与 `ethtool` 能给出的信息多得多。

## 岔路口二：IP 层 —— 能不能到

`ping` 是最常用的命令，也是**最容易被误读的**命令。

### ping 通说明了什么？

**只说明：ICMP Echo Request 到了对面，且 Echo Reply 回来了。**

它**不**说明：
- 端口开着（ping 通和 22/80/443 通不通完全无关）
- 应用正常
- 带宽够用
- 没有丢包（一次成功不代表持续稳定）

**所以"能 ping 通"几乎什么都不能证明。** 反过来，
"ping 不通"也未必是坏事 —— 很多服务器**故意**禁 ICMP，
但它上面的 Web 服务好好的。

### 真正有用的用法

```bash
# 别只 ping 4 次就下结论，跑够次数看丢包率
ping -c 100 10.10.122.1

# 指定源地址（多网卡机器上必须，否则可能从错误的网卡发出）
ping -I 192.168.10.50 10.10.122.1

# 大包探测 MTU / 分片问题
ping -M do -s 1472 10.10.122.1
```

最后一条特别有用。**`-M do -s 1472` 的意思**：

- `-s 1472`：ICMP 载荷 1472 字节
- `-M do`：禁止分片
- 加上 8 字节 ICMP 头 + 20 字节 IP 头 = **1500 字节**，正好一个标准以太网帧

如果这个能通而更大的包不通，**说明链路上有 MTU 限制**
（PPPoE、隧道、VPN 都会遇到）。这就是经典的 PMTUD 黑洞问题。

```
$ ping -M do -s 1472 10.10.122.1
ping: local error: message too long, mtu=1492    ← PPPoE 环境！MTU 是 1492 不是 1500
```

看到 `mtu=1492` 就明白了 —— 这是 PPPoE 的典型值，
如果应用层还按 1500 发大包，就会被静默丢弃。

## 岔路口三：路由 —— 走的路对不对

`traceroute` 告诉你包经过了哪些跳，但它有很强的误导性。

### 为什么 traceroute 中间出现 `* * *` 不一定是故障

`*` 表示那一跳没有回 ICMP Time Exceeded。
**很多路由器和防火墙默认不回复**，或者限速回复。
所以中间几跳全是 `*`、但最后一跳能到，是**完全正常**的。

```
$ traceroute 8.8.8.8
 1  10.10.122.1        2.1 ms
 2  * * *                                    ← 正常，中间设备不回
 3  202.96.x.x        12.4 ms
 4  8.8.8.8           28.7 ms                ← 到达了，所以前面 * 无所谓
```

**只看最后一跳能不能到，别被中间的 `*` 带偏。**

### mtr 比 traceroute 有用得多

`traceroute` 是一次性快照，`mtr` 是**持续统计**：

```bash
# 报告模式，跑 100 个包，看每一跳的丢包率
mtr -r -c 100 8.8.8.8

# 更详细的输出，含 AS 号和 IP 归属
mtr -rwzc 100 8.8.8.8
```

关键读法：**看丢包从哪一跳开始"持续"出现。**

```
HOST                Loss%   Snt   Last   Avg  Best  Wrst
1. 10.10.122.1       0.0%   100    2.1   2.3   1.8   5.2
2. 202.96.x.x        0.0%   100   12.4  12.9  11.2  35.1
3. 61.x.x.x          2.0%   100   13.1  14.0  11.8  89.3   ← 开始丢
4. 8.8.8.8           2.0%   100   28.7  29.5  27.1 120.4   ← 丢包率一致，说明是第 3 跳引入的
```

**第 3 跳丢 2%、第 4 跳也是 2% 且不再增长 → 问题在第 3 跳。**
如果第 3 跳丢 2% 但第 4 跳是 0%，那第 3 跳的丢包只是它不优先回 ICMP，
不是真丢。

## 岔路口四：端口 —— 服务在不在

ping 通只能证明 IP 可达，**端口才是"业务"的入口**。

```bash
# nc（netcat）：最直接的端口探测
nc -zv 10.10.122.50 443        # 成功：Connection to ... succeeded!
nc -zv 10.10.122.50 3306       # 失败：Connection refused / timed out

# 批量扫几个端口
nc -zv 10.10.122.50 22 80 443 3306
```

**`refused` 和 `timed out` 是完全不同的两种故障**，
这个区别很多人不区分，但它是定位的关键：

| 结果 | 含义 | 排查方向 |
|---|---|---|
| `succeeded` | 端口开着，TCP 握手完成 | 问题在应用层 |
| `Connection refused` | **有主机应答了 RST** | 主机活着，但**没有程序监听**这个端口 |
| `Connection timed out` | 没有任何回应 | **被防火墙 DROP 了**，或者路由不通 |

**`refused` 说明包到了主机、主机主动拒绝** ——
所以网络是通的，是服务没起来。这时候该去查服务进程，
而不是查防火墙。

**`timed out` 才是网络层/防火墙问题。**

> 这个区分帮我省过很多时间：客户说"数据库连不上"，
> 我一 `nc` 是 `refused` —— 直接告诉他"去启动 MySQL"，
> 而不是去查防火墙策略。30 秒定位。

## 岔路口五：DNS —— 名字解析对不对

前面四层都通了，仍然可能"网站打不开"。

```bash
# 看用的是哪个 DNS 服务器
cat /etc/resolv.conf          # Linux
ipconfig /all                 # Windows

# 直接问指定 DNS，绕过本地缓存
nslookup feiyuqifei.github.io 8.8.8.8
dig feiyuqifei.github.io @1.1.1.1 +short
dig feiyuqifei.github.io @1.1.1.1 +trace    # 从根域开始追踪解析过程

# 对比：本地解析 vs 公共 DNS 解析结果是否一致
dig feiyuqifei.github.io +short
dig feiyuqifei.github.io @8.8.8.8 +short
```

**两个结果不一致 → 本地 DNS 有问题**（缓存污染、配置错误、
或者被劫持）。这个对比方法一眼就能判定。

### 一个常见的认知错误

"能 ping 通 IP，但 ping 不通域名"——
**这不代表网络不通，只代表 DNS 有问题。**
两者是完全独立的两个环节。

反过来也成立：`nslookup` 能解析出 IP，
不代表那个 IP 可达。

## 岔路口六：应用层 —— 到这里才是业务

前五层都正常，问题就在应用层。这时候要用**抓包**。

```bash
# 抓 443 端口的包，写文件供后续分析
tcpdump -i eth0 -nn -s0 -w /tmp/cap.pcap 'tcp port 443'

# 实时看，只看 TCP 标志位和序列号
tcpdump -i eth0 -nn 'tcp port 443' -c 50

# 抓某个特定主机的所有流量
tcpdump -i eth0 -nn host 10.10.122.50 and not port 22
```

### TLS 握手失败怎么看出来

```
# 能看到的：客户端发了 Client Hello，服务器没回
10.10.122.50.54321 > 93.184.216.34.443: Flags [S], seq 1234567
93.184.216.34.443 > 10.10.122.50.54321: Flags [S.], seq 7654321, ack 1234568
10.10.122.50.54321 > 93.184.216.34.443: Flags [.], ack 1
10.10.122.50.54321 > 93.184.216.34.443: Flags [P.], length 517    ← Client Hello
                                                                    ← 没有 Server Hello！
```

TCP 三次握手完成了（能看到 `[S]` `[S.]` `[.]`），
客户端也发了 Client Hello（`length 517`），
**但服务器没有回应** —— 这通常意味着：

- SNI 被中间的防火墙拦截（根据域名阻断）
- 服务器上的证书配置有问题，直接拒绝
- 中间设备做了 TLS 检测并阻断

**看得到 TCP 握手成功、看不到 TLS 完成** ——
这个模式非常典型，一眼就能把问题范围从"网络不通"
缩小到"TLS/防火墙策略"。

## 我的排障清单（按顺序，别跳步）

1. **问清"不通"的具体含义**（谁、什么协议、什么时候开始、范围）
2. **换设备/换网络复现**，确定是单机还是全网
3. **链路层**：`ethtool` 看速率与双工
4. **IP 层**：`ping` 够次数看丢包；大包测 MTU
5. **路由**：`mtr` 看丢包从哪跳开始
6. **端口**：`nc -zv` 区分 `refused` 与 `timed out`
7. **DNS**：本地与公共 DNS 结果对比
8. **应用层**：`tcpdump` 看握手与 TLS 是否完成

**任何一步"正常"都不要当作通过** —— 要问"它证明了什么"。
`ping` 通只证明了 ICMP 能往返，仅此而已。

## 最后：两个思维习惯

**第一，先定性再定量。**
别一上来就抓包看十六进制。先确定"哪一层断了"，
再往下钻。层次划分的意义就在于此。

**第二，改动一次只改一处。**
我年轻时候犯过的错：同时改了防火墙策略、
DNS 配置和路由，然后问题消失了 —— 但**不知道是哪一处起了作用**。
两个月后再出同样的问题，还是不会查。

**排障的目标不只是"修好"，还包括"搞清楚为什么"。**
前者让你今晚能下班，后者让你明年不用再加班。
