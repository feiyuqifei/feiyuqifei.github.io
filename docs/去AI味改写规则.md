# 文章改写规则（去 AI 味）

这份规则用于改写博客里带「机器味」的文章。要求是可验证的，
不是「写自然点」这种无法执行的建议。

## 背景

站长的原话是「所有文章的风格太像 ai 了吧」。用 `pnpm run check:style`
量化后，问题集中在四处：

| 指标 | 超标文章 | 人类写作基准 | 已达标的样板 |
|---|---|---|---|
| 破折号密度（每千中文字符） | 4.4 ~ 7.2 | < 1.5 | 0.0 |
| 加粗密度 | 15.4 ~ 30.9 | < 8 | 3.9 |
| 末尾小节标题 | 「最后：xxx」「最后」共 7 篇 | 无固定套路 | 无 |
| 段落长度 CV | 0.57 ~ 0.65（太均匀） | > 0.68 | 0.71 |

**样板**：`src/content/posts/tech/network-troubleshooting.md` 与
`src/content/posts/tools/vmware-kali-setup.md`，改完应对齐它们的手感。

## 硬性指标（改完必须满足）

1. **破折号密度 = 0**。中文破折号「——」一个都不要用。要转折就换句号或逗号。
2. **加粗密度 < 8**（每千中文字符）。加粗只留给「读者照着做会出错的地方」，
   不要用来强调语气。整篇加粗总数尽量控制在 5 处以内。
3. **段落长度 CV > 0.68**。刻意让段落长短错落：有的一句话成段，
   有的五六行。均匀的段落是机器味最主要的来源之一。
4. **末尾小节标题不能是固定套路**。禁用「最后」「最后：xxx」
   「总结」「小结」「写在最后」「结语」。可以叫「两个习惯」
   「容易踩的三个坑」这类具体而随意的名字，或者干脆不设末尾小节。
5. **不要「总—分—总」结构**。结尾不要升华、不要上价值、
   不要「希望本文能帮到你」这类客套。
6. **第一人称要有具体场景**。不要通篇「我认为」。
   该出现「客户报了…」「同学问我…」「上次在机房…」这种带场景的句子。

## 内容保护（改写时绝对不能动）

- **技术要点一个不能少**。命令、参数、过滤器、端口号、
  协议名、报错原文全部保留。
- **代码块原样保留**，包括注释。
- **表格内容保留**（表格本身是信息密度的优点，不要为了「不像 AI」删掉）。
- **站内链接保留**（`/tech/xxx/` 这类），外链同理。
- frontmatter 的 `title`、`description`、`pubDate`、`tags`、`category`
  一律不动。`featured` 也不动。
- 不要新增没把握的技术论断。宁可少写，不要编。

## 改什么

### 1. 拆掉「加粗即强调」的习惯

原：`**抓包是手段，不是目的。** 这篇讲的是怎么用最少的时间…`

改：把句子本身写清楚，让人自然读到重点。
若确实需要一个提醒，用一整句写出来，而不是加粗半句。

### 2. 把破折号改成句号或分句

原：`这是抓包分析里最有价值的技巧之一，也是最容易被忽略的 —— 很多人只在一台机器上抓`

改：`这是抓包分析里最有价值的技巧之一，也最容易被忽略。很多人只在一台机器上抓，然后对着"没有响应"得出错误结论。`

### 3. 打散段落节奏

原（三段等长，每段 2 行）：
```
一种是抓包上瘾的人。一有问题就开 Wireshark，
抓下来几万个包，在十六进制里翻两个小时，
最后发现是网线没插好。

抓包是手段，不是目的。
```

改：插入一句独立成段的短句，再展开长的。
短句可以是判断、可以是反问、可以是一句吐槽。

### 4. 换掉末尾的升华段

原：
```
## 最后：一句反直觉的话

抓包高手和新手的区别，不在于能看懂多少协议细节，
而在于知道什么时候不需要抓包。
```

改：把这段的**信息**合并进正文合适的位置，
或者改成一个具体的小节（例如「什么时候不该抓」），
不要单独留一节做总结升华。

### 5. 让「我」有场合

少写「我认为 X」，多写「上次遇到一个情况，客户说…」。
具体场景比抽象论断可信得多，也更像人写的。

## 验证方法

改完后必须跑：

```bash
pnpm run check:style
```

看自己那篇的三个数字：破折号应为 `0(x.x)`，加粗应 < 8，
段长 CV 应 > 0.68。另外跑 `pnpm run check:md` 确认没有未解析的
Markdown 强调标记，跑 `pnpm run build` 确认构建通过。
